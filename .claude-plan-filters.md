## Combobox component API

```tsx
// ui/src/components/Combobox.tsx
export interface ComboboxOption {
	value: string;      // what gets written into Filters (workflowId or user.name)
	label: string;       // what's shown in the closed input AND the option row
	searchText?: string; // extra text matched on but not shown (e.g. raw workflowId); defaults to label
}

interface ComboboxProps {
	id: string;                 // mirrors existing id="f-workflow"/"f-user" for TipLabel's htmlFor
	options: ComboboxOption[];
	value: string;               // current Filters.workflow / Filters.user ("" = All)
	onChange: (value: string) => void;
	allLabel: string;            // "All workflows" / "All users" — the clear-selection row
	placeholder?: string;        // e.g. "Search workflows…" / "Search users…"
	emptyText?: string;          // "No matches" default
}
```

`FilterBar.tsx` usage sketch:

```tsx
<Combobox
	id="f-workflow"
	allLabel="All workflows"
	placeholder="Search workflows…"
	options={workflows.map((w) => ({
		value: w.workflowId,
		label: `${w.name} · ${shortId(w.workflowId)}`,
		searchText: `${w.name} ${w.workflowId}`,
	}))}
	value={filters.workflow}
	onChange={(workflow) => set({ workflow })}
/>
```

```tsx
<Combobox
	id="f-user"
	allLabel="All users"
	placeholder="Search users…"
	options={users
		.filter((u) => u.name !== "anonymous")
		.map((u) => ({ value: u.name, label: `${u.name} (${u.events} events)`, searchText: u.name }))}
	value={filters.user}
	onChange={(user) => set({ user })}
/>
```

Both call sites keep producing a plain `string` via `set({ workflow })` /
`set({ user })`, so `Filters` and `onChange` need zero changes. The
`workflowOptions` "keep the selected workflow present even if the live list
drops it" logic in `App.tsx` continues to work unmodified, since the
Combobox only renders whatever `options` it's given — same as the old
`<select>` — and falls back to showing the raw `value` as typed text if it's
selected but absent from `options` (see "Selected-but-missing value" below).

## Filtering logic

- Internal state: `open: boolean`, `query: string` (the text typed while
  open), plus a derived `activeIndex: number` for keyboard nav.
- Closed-state display: input's visible value is the `label` of the option
  matching `value`, or `allLabel` if `value === ""`, or the raw `value` string
  itself if it's non-empty but matches no option (keeps the App.tsx
  "preserve selected id not in the live list" behavior visible instead of
  silently blanking the box).
- On focus/click, open the listbox and seed `query` as `""` (show the full
  list first; the current selection is still visually indicated via
  `aria-selected`/a check or highlighted row, not by pre-filling text the
  user would have to clear).
- On every keystroke in the input, update `query` and recompute filtered
  options: case-insensitive substring match —
  `option.searchText.toLowerCase().includes(query.toLowerCase().trim())`
  (trim leading/trailing whitespace in the query only; no fuzzy matching, no
  highlighting of matched text — keep it simple like the rest of the panel).
- `allLabel` is always shown as the first row when `query` is empty; when
  `query` is non-empty, filter it out unless it matches "all" literally is
  not needed — simplest: always keep the "All …" row pinned at the top
  regardless of query, so clearing is always one click away even mid-search.
- If the filtered list (excluding the pinned "All" row) is empty, render a
  single disabled/aria-live row with `emptyText` ("No matches") instead of
  the listbox options.
- Selecting an option (click or Enter on the active row) sets `value` via
  `onChange(option.value)` (or `""` for the "All" row), clears `query`,
  closes the list, and returns focus to the input showing the new label.
- No local caching/memoization is strictly required given list sizes
  (hundreds, not thousands) — a plain `.filter()` on every keystroke is fine
  performance-wise; wrap in `useMemo([options, query])` only to avoid
  re-filtering on unrelated re-renders (e.g. other filters changing cause
  `FilterBar` to re-render with a new `workflows` array reference from
  `App.tsx`'s `useMemo`, but `query`/`value` for an untouched combobox
  wouldn't have changed, so memoizing on `[options, query]` is correct and
  cheap).

## Keyboard / ARIA behavior

Follow the standard "combobox with listbox popup, list autocomplete with
manual selection" WAI-ARIA pattern:

- Container: `<div className="combobox">` wraps an `<input role="combobox"
  aria-expanded aria-controls={listId} aria-autocomplete="list"
  aria-activedescendant={activeId}>` plus a `<ul role="listbox" id={listId}>`
  of `<li role="option" id={optionId} aria-selected>`.
- `htmlFor`/`id` on the input stays `f-workflow`/`f-user` so the existing
  `TipLabel htmlFor` wiring needs no change.
- **ArrowDown**: open the list if closed (seeding `activeIndex` at the
  current selection or 0); otherwise move `activeIndex` to the next row,
  clamped (no wraparound, matches most native comboboxes) or wrapping to the
  first — either is acceptable; pick clamped for simplicity.
- **ArrowUp**: symmetric, moves `activeIndex` back; clamps at the pinned
  "All" row (index 0).
- **Enter**: if the list is open and a row is active, select it (same as
  click) and close; if the list is closed, no-op.
- **Escape**: if open, close the list and revert the visible text to the
  current committed `label` (discard in-progress `query`) without changing
  `value`; do not bubble further (`stopPropagation` not required since
  nothing else listens, but harmless to add for safety against Modal's
  capturing listener if the combobox is ever used inside one).
- **Tab**: natural browser behavior — closes the list (via blur/click-outside
  handler) and moves focus on; do not trap focus (this is not a modal).
- **Click outside**: a `mousedown`/`click` document listener (added only
  while `open`, removed on cleanup — same effect-lifecycle shape as
  `Modal.tsx`'s keydown listener) that closes the list when the click target
  is outside the combobox's root ref.
- **Typing**: any printable keystroke while focused opens the list (if not
  already open) and updates `query`; does not immediately commit a `value`.
- Clicking the "All …" row or an option row: commits, closes, calls
  `onChange`, and returns focus to the input (so a screen-reader user lands
  back where they started, consistent with native `<select>` behavior).
- Empty state row: `role="option"` is NOT appropriate for a non-selectable
  placeholder — render it as a plain `<li role="presentation">No
  matches</li>` (or `aria-disabled="true"` on a dummy option) so AT doesn't
  announce it as a selectable item.

## Risks

- **Selected-but-absent value**: `App.tsx`'s `workflowOptions` can include a
  synthetic `{ workflowId: filters.workflow, name: ... }` entry specifically
  to keep a filtered-out workflow selectable/visible (lines 373-379) — the
  Combobox must resolve `value` → display label by first checking `options`
  for a match, and only falling back to showing the bare `value` string if
  truly absent from `options` (should not happen in practice since App.tsx
  already guarantees presence, but the component shouldn't crash or blank out
  if some other caller omits that safeguard).
- **Typeahead vs. committed value divergence**: while the user is typing a
  query that doesn't yet match the committed `value`'s label, the input must
  show the typed `query`, not the stale committed label — need a clear
  "controlled display value" rule: show `query` while `open && query !== ""`,
  otherwise show the resolved label for `value`.
- **Perf with 200+ workflows**: substring filtering on every keystroke across
  ~200-300 rows is trivial (<1ms), no virtualization needed; if `workflows`
  ever grows an order of magnitude, revisit, but out of scope here.
- **Clicking the chevron / native look**: dropping the native `<select>`
  loses the OS's built-in affordances (native scrollbar, native mobile
  picker UI). On touch/mobile this custom listbox needs large enough tap
  targets (`.combobox-option` padding already ~`var(--space-2)
  var(--space-3)` ≈ 8px/12px, should be bumped if testing shows it's too
  tight) and must not break when the on-screen keyboard covers the viewport
  bottom — acceptable risk, not blocking, but worth a manual check in step 3.
- **Two-row layout reflow when `range === "custom"`**: adding From/To fields
  dynamically shifts which named field lands in which grid cell (the task's
  suggested row split assumes no From/To); with the explicit 4-column
  template this just adds a 3rd row rather than corrupting layout, but it
  means the panel is sometimes 2 rows and sometimes 3 — acceptable and matches
  "should wrap gracefully," just noting it's not always exactly two rows.
- **z-index stacking**: `.combobox-list` using `z-index: 50` must not be
  hidden under the `.topbar`'s own `z-index: 50` (line 136) if the Workflow/
  User fields are near the top of a short viewport and the list opens
  upward into the header area; in practice the Filters panel sits well below
  the topbar in normal scroll position so this is low risk, but step 2/3
  should visually confirm the dropdown isn't clipped by `.panel`'s
  `overflow` (currently `.panel` sets no `overflow`, so clipping is unlikely,
  but confirm).
- **Existing `TipLabel` tooltip**: `title={tip}` is on the `<label>`, not the
  control, so switching the control from `<select>` to the Combobox's
  `<input>` doesn't disturb the tooltip; just confirm `htmlFor` still points
  at the Combobox's inner `<input id="f-workflow">`/`id="f-user"` element
  (not the outer wrapper div) so clicking the label focuses the input like
  before.
- **No regression to `active` filter-chip logic**: `FilterBar`'s `active`
  boolean (line 65-67) reads `filters.user`/`filters.workflow` directly from
  props, unaffected by the Combobox swap since the `Filters` shape is
  unchanged.

### Defects found during review and fixed

1. **Dropdown stayed open after Tab-away.** The combobox only closed on
   Escape, a selection, or an outside click (`mousedown` captured on
   `document`) — pressing Tab to move focus elsewhere left the listbox
   rendered and floating over whatever the operator tabbed into next.
   Fixed by adding an `onBlur={closeList}` handler on the input. To keep
   this from breaking mouse selection (clicking a non-focusable `<li>` can
   blur the input before its `click` handler fires, which would unmount the
   option before the click registers), `onMouseDown={(e) =>
   e.preventDefault()}` was added to the `<ul className="combobox-list">` so
   option clicks no longer blur the input in the first place; the blur
   handler then only fires for genuine focus-outs (Tab, or focus moving to
   another real control). Extracted the shared close logic into one
   `closeList()` helper used by Escape, outside-click, and blur, so all three
   close paths stay in sync.
2. **`.combobox-list` shared `z-index: 50` with `.topbar`.** Both were the
   same value, so correct stacking relied on DOM order (the filter bar
   renders after the topbar, so ties resolved correctly today) rather than
   an explicit, order-independent rule — the exact risk flagged in the
   investigation step. Bumped `.combobox-list` to `z-index: 60` so the open
   listbox is unambiguously above the sticky header regardless of future
   DOM reordering.
