Implementation plan · server auth

Authentication for the report server

Put a login in front of target-server. JWT-based sessions, a seeded default operator (admin@admin.com), a Users section that creates and deletes accounts, emails validated by a joi blueprint, an invitation email whose single-use link is where the new user sets their own password, and a login page with password recovery — on a server that is being deployed, so the defaults are chosen for a public bind, not for 127.0.0.1.

Revised 2026-08-26 against the answers to §16: validation is joi, no password is ever emailed, mail goes through a real relay, every user is an admin, and the server ships to a deployment. Two runtime dependencies (joi, nodemailer) — the first this repo has ever had, and §16 says what each one bought.

1Where we are today

target-server is a single Node ≥24 process (server.mjs, ~250 lines) with no runtime dependencies: node:http, node:sqlite and friends. (This plan spends that budget for the first time — two packages, justified one by one in §3.) db.mjs owns the schema and every query; ui/ is a React 19 + Vite SPA that builds to public/dist/ and is served as static files.

  • Nothing is authenticated except ingest. TARGET_INGEST_TOKEN — when set — guards POST /ingest with a shared bearer token. Every GET /api/* route (stats, instances, users, events, workflows, workflows/:id) is open to anyone who can reach the port, as is the dashboard itself.
  • /api/users already exists and is not about people. It returns distinct reporting instance display names. The new human accounts must not collide with it — see §7.
  • Routing is a flat if chain in the createServer callback, with serveStatic as the fallback for any other GET. Unknown paths 404 — there is no SPA fallback, which matters the moment we introduce /login and /reset URLs.
  • The SPA has no router and no client state beyond filters. App.tsx renders the whole dashboard unconditionally; hooks/useApi.ts is a thin fetch + poll helper that reports errors as strings and has no notion of a 401.
  • Schema evolution is CREATE TABLE IF NOT EXISTS inside open(). There is no migration framework, and for additive tables we do not need one.
  • Tests (test/*.test.mjs) boot the real server on an ephemeral port against a temp DB and hit the HTTP API directly. Four files today: ingest, notes, pagination, usage.

3Design decisions (and why)

D1 · Two dependencies, and no third

The zero-dependency posture is documented in the README, in package.json and in the CI workflow's comments, and this plan breaks it — deliberately, twice. The rule it replaces: a dependency is worth it when it owns a protocol or a spec we would otherwise re-implement badly, and not when it owns code we can read in one sitting.

PackageVersionWhy it earns its place
joi ^18.2.5 Asked for by name. It owns the validation vocabulary (§4), including string().email() with real TLD data — the one rule nobody should hand-roll. Server-side only; see D8.
nodemailer ^9.0.5 Owns SMTP. The previous draft hand-rolled EHLO/STARTTLS/AUTH/ quoted-printable over node:net. On a deployed server the invitation mail is the only path to an account (D7), so that protocol code moved from "clever" to "single point of failure". Nodemailer has zero runtime dependencies of its own — the tree stays two packages deep, total.

Still hand-rolled: the JWT. Now that the rule is a budget rather than a ban, jsonwebtoken deserves re-asking — and the answer does not change. A JWT is three base64url segments and one HMAC-SHA256; node:crypto gives us that in ~40 lines with timingSafeEqual. What the library really sells is breadth of algorithms (RS/ES/PS) we will never use, and its historical CVEs are precisely the alg-confusion class that D3's literal "HS256" check closes in one line. It owns nothing we cannot read.

D2 · scrypt for password hashing

crypto.scrypt is a memory-hard KDF in the standard library — no bcrypt/argon2 native build. Store scrypt$N$r$p$<salt-b64>$<hash-b64> so the parameters travel with the hash and can be raised later without breaking existing rows. Verify with timingSafeEqual.

D3 · The token lives in an httpOnly cookie, and the header still works

The dashboard is same-origin with the API, so a cookie is the simplest transport and the one that survives XSS better than localStorage. Set HttpOnly; SameSite=Strict; Path=/; Max-Age=… (plus Secure when TARGET_AUTH_SECURE_COOKIE=1, since the default bind is plain HTTP on 127.0.0.1). The middleware also accepts Authorization: Bearer <jwt>, so curl and scripts are not locked out.

D4 · One short-lived access token + a token_version, not a refresh-token table

A refresh-token table is the textbook answer, but this is a single-operator monitoring tool and the real requirement behind it is "deleting a user must actually log them out". A token_version integer on the user row does that in one comparison: the claim carries tv, the guard rejects any token whose tv no longer matches. Deleting a user, changing a password or resetting one all bump it. Token TTL: 8 hours (an operator's working day), re-issued on any authenticated request older than half its life so an active session slides forward.

D5 · Ingest keeps its own auth — the fleet must not break

POST /ingest is machine-to-machine and already has TARGET_INGEST_TOKEN. It stays exactly as it is. Reporting instances in the field must not need a JWT, and a deploy of this feature must not drop a single batch.

D6 · The dashboard bundle stays public; the data does not

public/dist/* is served unauthenticated — it has to be, or there is nothing to render the login page with. The bundle contains no secrets. Everything under /api/ except /api/auth/* requires a session.

D7 · An invitation link, not a mailed password (new)

Creating a user no longer asks the creator to invent a password. The account is stored with no usable password hash and one single-use invitation token; the email carries /setup?token=…, and the user's first password is the one they choose there. This removes the credential-in-a-mailbox problem the previous draft could only mitigate, and it deletes a whole state — there is no must_change_pw modal to build, because a user who has not completed setup has no password to change.

The cost is that mail is now on the provisioning critical path: an undelivered invitation is an account nobody can enter. Three things pay for it — the create response returns the invitation URL so the Users panel can offer Copy link for out-of-band delivery, a Resend action re-issues it, and the server refuses to boot with a non-delivering transport when it is publicly bound (§17).

D8 · The blueprint runs on the server only (new)

The previous draft shared blueprint.mjs with the browser through a Vite alias so "the form and the endpoint can never disagree". With joi as the engine that trade turns bad: joi's browser build is 178 KB minified / ~53 KB gzipped, against a current dashboard bundle of 232 KB / 73.5 KB — a +72% gzipped payload to check an @ and a string length.

Worse, it would not even buy the guarantee. Two copies of a rule agree only while the bundle is fresh, and this repo has just shipped a fix for exactly that failure — a device serving a stale public/dist against a newer API. The way to make the form and the endpoint agree is to have one implementation, on the side that enforces it: the form posts, the endpoint answers 422 { errors: [{ field, code, message }] }, and the form renders those errors under the right inputs. The client keeps only what costs nothing and cannot drift — required, type="email", minlength="12" — for instant feedback before the round trip.

If a future form is complex enough to want the real schema in the browser, joi's ESM browser build can be await import()-ed inside that one component, so the dashboard pays for it only on the page that uses it. Nothing in this plan needs that.

4The blueprint: one validation source of truth

Answered — Q1

"Blueprint" is joi. The previous draft guessed at declarative-validation-in-general and hand-rolled the combinators; that guess is now gone. blueprint.mjs keeps its name, its place and its public contract — only the engine underneath is joi instead of forty lines of our own.

blueprint.mjs (repo root, ESM) declares one named joi schema per request shape and exports a single validate(). It is the single source of truth for validation, imported by server.mjs and by nothing else — the browser does not run it (D8), it renders the errors it comes back with. 

// blueprint.mjs
import Joi from "joi";

const EMAIL = Joi.string().trim().lowercase().max(254)
  .email({ minDomainSegments: 2, tlds: { allow: true } })   // real TLD list, not a regex
  .required();

const PASSWORD = Joi.string().min(12).max(200).required();  // length only, no composition theatre
const TOKEN    = Joi.string().hex().length(64).required();  // sha256-sized invite/reset token

export const BLUEPRINTS = {
  "user.create":  Joi.object({ email: EMAIL }),                    // no password: the invite sets it (D7)
  "auth.login":   Joi.object({ email: EMAIL, password: Joi.string().required() }),
  "auth.forgot":  Joi.object({ email: EMAIL }),
  "auth.setup":   Joi.object({ token: TOKEN, password: PASSWORD }), // invitation → first password
  "auth.reset":   Joi.object({ token: TOKEN, password: PASSWORD }), // recovery → new password
};

const OPTS = { abortEarly: false, stripUnknown: true, convert: true };

/** → { ok: true, value } | { ok: false, errors: [{ field, code, message }] } */
export function validate(name, input) {
  const { value, error } = BLUEPRINTS[name].validate(input ?? {}, OPTS);
  if (!error) return { ok: true, value };
  return { ok: false, errors: error.details.map(toFieldError) };
}
  • The error shape is ours, not joi's. toFieldError maps each detail to { field: d.path.join("."), code: d.type, message } — so the wire contract stays { field, code, message } exactly as the previous draft promised, the UI never learns what joi is, and swapping the engine again would not touch a single component. d.type gives stable codes (string.email, string.min, any.required); message comes from a small messages() override so users read "Enter a valid email address", not "email" must be a valid email.
  • Normalisation is part of validation. .trim().lowercase() with convert: true means validate() returns the cleaned value, and that is what gets stored and compared — so ADMIN@Admin.com and admin@admin.com are one account, not two. Every call site uses the returned value, never the raw body; that is the rule reviewers should check.
  • Email: joi's .email() with tlds: { allow: true } validates against the real IANA TLD list shipped in @hapi/tlds — the single strongest argument for the dependency, since it is the one rule a hand-written regex always gets wrong. minDomainSegments: 2 rejects user@localhost. Unicode addresses are accepted and stored as given; deliverability is still proven by the invitation email, not by a parser.
  • stripUnknown: true is a security control, not tidiness: a client cannot smuggle role, token_version or id into a create body, because fields the schema does not declare never reach the query.
  • Uniqueness is not a blueprint rule — it needs the DB. It is checked right after and surfaced in the same { field: "email", code: "email_taken" } shape, so the form renders a joi error and a database error through one code path.
  • No UI alias, no blueprint.d.ts. Both existed only to share the module with the browser; D8 drops that, which also drops the server.fs.allow: ['..'] hole in the dev server and the hand-written type file that would have had to track the schema by hand. ui/vite.config.ts is no longer touched by this plan.

5Data model

Two new tables in db.mjs's open(), additive, CREATE TABLE IF NOT EXISTS like everything else — an existing target-server.db upgrades in place with no migration step. 

CREATE TABLE IF NOT EXISTS auth_users (
  id             TEXT PRIMARY KEY,          -- uuid
  email          TEXT NOT NULL UNIQUE,      -- normalised by the blueprint
  password_hash  TEXT,                      -- NULL until the invite is completed (D7)
  role           TEXT NOT NULL DEFAULT 'admin',
  token_version  INTEGER NOT NULL DEFAULT 1,
  created_at     TEXT NOT NULL,
  created_by     TEXT,                      -- auth_users.id of the creator
  invited_at     TEXT,                      -- last invitation sent
  activated_at   TEXT,                      -- when they set their own password
  last_login_at  TEXT
);
CREATE TABLE IF NOT EXISTS auth_resets (
  token_hash  TEXT PRIMARY KEY,             -- sha256 of the emailed token
  user_id     TEXT NOT NULL,
  kind        TEXT NOT NULL DEFAULT 'reset',-- 'invite' | 'reset'
  created_at  TEXT NOT NULL,
  expires_at  TEXT NOT NULL,
  used_at     TEXT
);
CREATE INDEX IF NOT EXISTS idx_resets_user ON auth_resets(user_id);
CREATE TABLE IF NOT EXISTS auth_meta (      -- singleton: the signing secret
  id INTEGER PRIMARY KEY CHECK (id = 1),
  jwt_secret TEXT NOT NULL,
  created_at TEXT NOT NULL
);
  • Seeding (R2): at the end of open(), if auth_users is empty, insert admin@admin.com with password-target-server hashed, and log a loud warning that the default credentials are active. Seeding only on an empty table means deleting the admin on purpose does not resurrect it on the next restart — but see §7: you cannot delete the last user. Because the server is being deployed, TARGET_SEED_ADMIN_PASSWORD overrides the default, and the boot warning escalates to a refusal when the published default is still in place on a non-loopback bind (§17). This is the one account that can hold a password it did not choose, so it is the one account that still gets nagged to change it.
  • Tokens are stored hashed. The 32 random bytes go in the email; only their SHA-256 goes in the DB, so a database read does not hand over live links. Single use (used_at), 1 hour TTL for recovery, 7 days for an invitation (people read mail late). Expired rows are swept opportunistically. Issuing a new token of a kind invalidates that user's outstanding ones of the same kind, so Resend cannot leave two live invitations behind.
  • password_hash IS NULL is the invited-but-not-yet-set state (new). It is the only state change D7 introduces, and it is load-bearing in three places: login refuses it (and says "finish setting up your account", since there is nothing to compare against), the Users panel renders it as a Pending badge with Copy link / Resend, and auth.setup is the one endpoint allowed to fill it. A user in this state still counts for the last-user guard — deleting the only activated admin because a pending invitation exists would lock the instance out.
  • must_change_pw is gone. It existed to chase a mailed password out of a mailbox. No password is mailed, so there is nothing to chase, and the first-login modal it drove is cut from §10. The seeded admin is the exception, handled below.
  • The signing secret comes from TARGET_AUTH_SECRET when set. Otherwise one is generated (randomBytes(32)) and persisted in auth_meta, so a restart does not silently log everyone out — with a log line saying where it came from.

6JWT, cookies and revocation

auth.mjs (new, zero-dep) owns the whole mechanism:

signJwt(payload)            // { alg: "HS256", typ: "JWT" } + HMAC, base64url
verifyJwt(token)            // → payload | null  (timingSafeEqual, exp checked)
hashPassword(plain)         // scrypt$N$r$p$salt$hash
verifyPassword(plain, hash)
readToken(req)              // Cookie: target_auth=… | Authorization: Bearer …
authenticate(req)           // → user row | null   (verifies tv against the DB)
requireAuth(req, res)       // → user | writes 401 and returns null
setAuthCookie(res, jwt) / clearAuthCookie(res)

Claims: { sub, email, role, tv, iat, exp }. Nothing secret, nothing large. alg is checked against the literal "HS256" before verification — the alg: none confusion attack is a two-line mistake to make and a one-line check to prevent.

7API surface

Naming

GET /api/users already means "distinct reporting instance display names" and the dashboard's filter bar depends on it. Human accounts therefore live under /api/auth/users, and the old route keeps its meaning and its shape. No breaking change for the SPA or for anyone scripting against it.

RouteAuthBody / paramsReturns
POST /api/auth/login public blueprint auth.login 200 { user } + Set-Cookie; 401 { error: "invalid_credentials" } — identical for unknown email, wrong password and an account whose invitation is still pending (password_hash IS NULL; there is nothing to verify, and saying so would be an enumeration oracle)
POST /api/auth/logout session — 204 + cookie cleared
GET /api/auth/me session — 200 { user } / 401. This is the SPA's boot probe: its answer decides login page vs dashboard
POST /api/auth/forgot-password public blueprint auth.forgot Always 202 { ok: true } — an honest 404 here is an account-enumeration oracle. Mail is sent only if the account exists
POST /api/auth/setup (new) token blueprint auth.setup The invitation link's endpoint (D7): sets the first password on an account whose password_hash is NULL, stamps activated_at, consumes the token, and signs the user in. 400 { error: "invalid_or_expired" }; 409 already_activated if the account already has a password — that user wants recovery, not setup, and the response says so
POST /api/auth/reset-password token blueprint auth.reset 200 + auto-login; 400 { error: "invalid_or_expired" }. Consumes the token, bumps token_version
GET /api/auth/users session — { users: [{ id, email, role, createdAt, lastLoginAt }] } — never the hash
POST /api/auth/users session blueprint user.create — email only 201 { user, invite: { url, expiresAt }, mail: { sent, transport } }; 409 email_taken; 422 with the blueprint's errors[]. invite.url is returned to the creating admin on purpose — it is the out-of-band escape hatch for undelivered mail (D7), and it is safe here because the caller is an authenticated admin who could invite the address again anyway. It is returned only in this response and never in GET listings
POST /api/auth/users/:id/invite (new) session — 200 { invite: { url, expiresAt }, mail: { sent, transport } }. Re-issues the invitation, invalidating the previous one. 409 already_activated for a user who has a password — they use recovery instead
DELETE /api/auth/users/:id session — 204; 409 last_user (never lock the instance out); 409 self_delete. Bumps token_version and drops pending resets, so the deleted user's cookie dies on their next request

Two shared concerns implemented once, in server.mjs: a JSON body reader for POST (reuse the existing readBody + a small readJson wrapper with the same 5 MB cap) and a rate limiter — an in-memory Map keyed by IP+route, 10 attempts / 15 min on login, forgot-password, reset-password and setup, answering 429 with Retry-After. In-memory is honest for a single-process server; it resets on restart and that is acceptable here. Deployed, the client IP comes from the last hop of X-Forwarded-For and only when TARGET_TRUST_PROXY=1 — trusting that header unconditionally would let anyone reset their own bucket by forging it (§17).

8Guarding what already exists

One insertion point in the createServer callback, placed after the /ingest, /health and /api/auth/* branches and before the data routes: 

// Public: /ingest (machine token), /health, /api/auth/*, and the static bundle.
// Everything else under /api/ needs a human session.
if (pathname.startsWith("/api/") && !requireAuth(req, res)) return;
  • /health stays public — liveness probes and uptime checks depend on it and it leaks nothing.
  • /ingest is untouched (D5).
  • SPA fallback: serveStatic gains one rule — a GET that is not under /assets/, has no file extension and does not resolve to a real file serves index.html instead of 404. Without it, /login and the emailed /setup?token=… and /reset?token=… links all break on refresh — and for an invited user that link is their first contact with the server, so a 404 there is the whole feature failing at the front door.
  • The "dashboard not built" 503 page keeps working, and gets one extra line telling the operator the API is guarded now. So does the "dashboard out of date" page added by the stale-bundle fix — both are served before the guard, because an operator who cannot log in needs to be told why, and neither page reveals anything.

9Sending mail: nodemailer, and a relay

Answered — Q3, "you should decide"

The decision: keep one SMTP config knob, stop writing the SMTP client. mailer.mjs becomes a ~60-line wrapper over nodemailer instead of ~200 lines of hand-rolled EHLO/STARTTLS/AUTH/ quoted-printable over node:net. Two answers forced this together: mail is now the only way into an account (Q2 → D7) and the server is going to be deployed (Q5), so "our SMTP client mis-parses one relay's multiline greeting" stops being a bug and starts being an outage nobody can log in through.

Relay: any provider that speaks SMTP — the config stays a single TARGET_SMTP_URL, so Resend, SES, Postmark, Mailgun and a corporate relay are all the same one-line change and none of them is baked into the code. If you want a default recommendation for this deployment: a transactional provider on your own domain with SPF and DKIM published, because an invitation that lands in spam is an account that never gets used. Sending from @gmail.com through a consumer account is the one option to avoid.

The transport table is unchanged in shape — the file and noop transports are what keep tests and CI working without a mail server — but the choice is now enforced at boot rather than merely defaulted:

TransportWhenBehaviour
smtp TARGET_SMTP_URL is set Real delivery through nodemailer.createTransport(url). smtp://user:pass@host:587 (STARTTLS) or smtps://…:465 (implicit TLS). Required when the bind is not loopback — see below. Verified once at boot with transport.verify(), which turns a wrong password into a startup error instead of a silently undelivered invitation an hour later
file default Writes .eml files to ./.mail-outbox/ (gitignored) and logs the path. Development and CI work end-to-end with no mail server, and the tests assert against those files
noop TARGET_MAIL_TRANSPORT=noop Drops the message, logs one line
Boot guard — the cost of D7

Starting with the file or noop transport while HOST is not a loopback address is refused: every invitation would be written to a directory on the server and read by nobody, and since no password is mailed, no invited user could ever log in. The error names the fix (TARGET_SMTP_URL) and TARGET_ALLOW_FILE_MAIL=1 overrides it for anyone who genuinely wants that. Locally — the default 127.0.0.1 bind — nothing changes: the file transport stays the default and CI never needs a mail server.

Mail must never fail user creation. Sending happens after the row is committed; a transport error is caught, logged, and reported as { mail: { sent: false, error } } so the Users panel can show "user created — invitation email failed" next to the Copy link and Resend actions, rather than a half-done operation the operator cannot interpret. With D7 that fallback is no longer a nicety: the returned invite.url is what an admin hands over by any other channel while the relay is being fixed.

The invitation email (R5, revised)

Plain-text plus a minimal HTML part. No credential appears in it — the link is the credential, and it expires: 

Subject: Your Target report server account

You have been given an account on the Target report server.

  Server:  https://target.example.com/
  Email:   someone@example.com

Choose your password to finish setting up the account
(link valid 7 days, single use):

  https://target.example.com/setup?token=…

If the link has expired, ask whoever invited you to send a new one.
If you were not expecting this, ignore this email — the account
cannot be used until someone opens the link.
Answered — Q2, and the risk it retires

The previous draft mailed the password because R5 said so, and flagged that this leaves a live credential sitting in at least two mailboxes forever. The answer chose the invite link, so that paragraph is now a paragraph about a risk we no longer take. What the change actually removes: a plaintext password in mail archives and backups, a password chosen by someone other than its owner, the must_change_pw column, and the first-login modal that enforced it.

What it adds is one failure mode, stated plainly: an account is unusable until its invitation is opened. That is why invite.url comes back to the admin, why Resend exists, and why the boot guard above refuses a non-delivering transport on a public bind. The recovery email is unchanged in shape — same template family, 1 hour TTL, /reset instead of /setup.

The link's origin comes from TARGET_PUBLIC_URL (default http://HOST:PORT) — never from the request's Host header, which an attacker controls and could use to redirect setup and reset links to their own domain. Deployed, it stops being optional: behind a proxy the default resolves to the internal bind (http://0.0.0.0:8900/), producing invitations nobody outside the host can open. The boot guard in §17 requires it for a non-loopback bind for exactly that reason.

10Dashboard: login, recovery, Users

  • AuthGate.tsx wraps <App/> in main.tsx. It reads location.pathname — /setup and /reset render their token forms even while logged out; everything else is decided by /api/auth/me. Three states: checking (a quiet splash — no dashboard flash), anonymous, signed in. Roughly 120 lines, no router dependency; the dashboard's existing URL-free filter state is untouched.
  • LoginPage.tsx — email + password, native required / type="email" for instant feedback and the server's errors[] for everything else (D8 — joi does not ship to the browser), one error line for bad credentials, and a "Forgot your password?" toggle that swaps in the recovery form and always shows the same "if that address has an account, a link is on its way" confirmation.
  • TokenPasswordForm.tsx (one component, two routes) — reads the token from the query string, takes a password twice, posts to /api/auth/setup or /api/auth/reset-password depending on the path, and on success drops straight into the dashboard (both endpoints set the cookie). The two differ only in copy — "Choose your password" versus "Set a new password" — and in what an expired token offers: setup says "ask whoever invited you to resend", recovery offers the forgot-password form again. Merging them is worth a line here because the previous draft had one form and now there are two flows through it.
  • UsersPanel.tsx — a panel in the existing App.tsx layout, matching InstancesTable's markup so it inherits global.css: a table of accounts (email, status, created, last login), a create form that is now a single email field and an Invite button — no password input, no Generate button, no crypto.randomUUID() password — and a delete button with a typed-email confirmation. Disabled with a tooltip for the last remaining user and for your own row. Status is Pending invitation or Active, and a pending row carries Copy link (the invite.url from the create response, held in component state only — it is never re-fetched, so a reload drops it and Resend is the way back) and Resend. After a create it shows the mail outcome, and on mail.sent: false it says so loudly with the link right there, because on a deployed server that is the difference between a stuck account and a phone call.
  • hooks/useApi.ts gains one behaviour: a 401 fires an onUnauthorized callback (context) instead of setting an error string, so an expired token drops every polling panel back to the login page at once rather than painting six red boxes. A usePost sibling handles the mutating calls, since the hook is GET-only today.
  • Top bar gains the signed-in email and a Sign out button next to the existing "live · refresh 4s" indicator.
  • The first-login modal is cut (was: "prompt when must_change_pw"). Nobody is issued a password they did not choose, so nobody needs to be chased into changing one — with a single exception: the seeded admin@admin.com. If the signed-in user is that account and it still holds the published default password, the top bar shows a persistent warning strip linking to the password change. One banner, not a modal, and it disappears the moment the password changes.

13Test plan

Existing tests will break — deliberately

ingest.test.mjs, notes.test.mjs, pagination.test.mjs and usage.test.mjs all hit /api/* unauthenticated. That is the correct new failure. Each gets a small login() helper in a shared test/helpers.mjs that logs in as the seeded admin and returns a cookie header — which also proves the seeded account works on a fresh DB, on every run. The ingest assertions themselves stay untouched, which is the regression signal that matters most.

  • blueprint — table-driven: valid and invalid emails (unicode, spaces, double @, no TLD, user@localhost, a made-up TLD, 300 chars), normalisation (" ADMIN@Example.COM " → admin@example.com), password length, stripUnknown drops an injected role, and the { field, code, message } shape — the last one is the contract the UI depends on, so it is asserted literally rather than snapshotted.
  • auth — login success/failure; identical response and timing shape for unknown email vs wrong password; cookie flags; me before/after; expired token rejected; tampered signature rejected; alg: none rejected; token_version bump invalidates a live cookie; Bearer header path; rate limiter 429s and recovers.
  • guard — every existing /api route 401s anonymously and 200s with a session; /health and /ingest still work without one; /login serves the SPA shell.
  • users — create (201 + row + no hash in the response + an invite.url), duplicate → 409, invalid email → 422 with the blueprint error, delete → 204 + the deleted user's cookie now 401s, last-user and self-delete → 409. A pending user counts toward the last-user guard, and a body carrying role: "superadmin" creates a plain admin.
  • invitation (new) — the .eml contains the address and the setup link and does not contain the string "password:" or any credential; opening the link sets a first password and signs in; the account cannot log in before that (and fails with the same invalid_credentials as a wrong password, not a distinguishable error); a second use of the token fails; an expired token fails; Resend invalidates the previous token; setup on an activated account → 409.
  • mail — an SMTP failure still returns 201 with mail.sent: false and a usable invite.url, which is the escape hatch D7 leans on; the file transport is refused on a non-loopback bind unless TARGET_ALLOW_FILE_MAIL=1.
  • recovery — forgot-password returns 202 for a nonexistent address and writes no mail; for a real one it writes mail and the link resets the password; the old password stops working.
  • boot guards (new) — with HOST=0.0.0.0, starting without TARGET_SMTP_URL, without TARGET_PUBLIC_URL, or with TARGET_AUTH_DISABLED=1 each exits non-zero with a message naming the variable; each override is honoured; none of them fire on the default loopback bind, so no existing local workflow changes.
  • UI — npm run build (tsc --noEmit strict + Vite) is the gate CI already enforces. Plus a bundle-size assertion: the built assets/*.js stays under 300 KB raw, which is what makes D8 a rule rather than an intention — an accidental import Joi from "joi" in a component fails CI instead of quietly adding 178 KB.

14Security notes

  • Enumeration: login and recovery answer identically whether or not the address exists — and identically for an account whose invitation is still pending, which is a third case the invite flow introduces and the easiest one to leak.
  • Timing: verify a dummy hash when the user is missing, so "no such user" costs the same as "wrong password". timingSafeEqual for every secret comparison.
  • CSRF: SameSite=Strict covers it for a same-origin SPA; the mutating routes additionally require content-type: application/json, which a cross-site form post cannot send.
  • Host-header injection: emailed links come from TARGET_PUBLIC_URL, never from the request.
  • Secrets in logs: the existing log() prints request context — the new code logs email addresses and user ids only, never passwords, tokens or hashes. Invitation and reset URLs are never logged either (they are bearer credentials for an account), and the mail body is not logged; the file transport writes it to disk, which is a dev-only path and gitignored.
  • No password is ever transmitted by mail (D7). The only credential the system originates is the seeded admin's, and it exists to be replaced.
  • Default credentials are, by definition, published. On a loopback bind that is a warning; on a public bind the server refuses to start until TARGET_SEED_ADMIN_PASSWORD is set or the password is changed. The README will say so plainly.
  • Dependency surface (new): two direct packages, joi pulling six @hapi/* modules and nodemailer pulling none. Both are on the request path for unauthenticated input, so npm audit in CI stops being a formality and the lockfile is now something reviewers read.
  • Not in scope: roles (Q4 — every user is an admin who can create and delete any other, including the one who created them), 2FA, SSO, account lockout, an audit log. The role column is written with 'admin' and never read; when a read-only viewer is wanted it is a query change, not a migration. Worth saying out loud: with no roles, an invitation is a full grant — anyone who receives one can delete everyone else. For a single-operator monitoring tool that is the accepted trade, and the last-user guard is the only floor under it.

15Acceptance criteria

  1. A fresh node server.mjs against an empty DB seeds admin@admin.com / password-target-server, and that account logs in through the browser.
  2. Loading / while signed out shows the login page, not the dashboard; no /api data is fetched or returned.
  3. Every /api/* route except /api/auth/* answers 401 without a session. /ingest and /health are unaffected.
  4. The Users panel creates a user from an email alone; a bad address is rejected by the joi blueprint with a message the form renders under the field, and the same body posted by curl is rejected identically.
  5. Creating a user produces an invitation email that contains a working single-use setup link and no password; opening it lets the invited user choose their own password and lands them in the dashboard signed in.
  6. Until that link is opened, the account cannot log in, and the attempt is indistinguishable from a wrong password.
  7. "Forgot your password?" sends a reset link that sets a new password and signs the user in; the old password stops working.
  8. Deleting a user removes it and invalidates its live session on the next request; the last remaining user cannot be deleted.
  9. On a non-loopback bind, the server refuses to start without a real mail transport, without TARGET_PUBLIC_URL, with auth disabled, or with the published default admin password still in place — each with a message naming the variable that fixes it.
  10. npm test and npm run build pass; the root package.json declares exactly joi and nodemailer, ui/package.json is unchanged, and the built dashboard bundle has not grown beyond its current size plus the new components.

16Answers, and what they changed

All five open questions are answered. The plan above is rewritten to match; this section is the decision log — what was asked, what came back, and which sections moved.

Q1 · "Blueprint" → joi

Answer: use the joi dependency. §4 is rewritten around joi@^18: five named schemas, one validate(), and a mapping layer that keeps the { field, code, message } wire shape the rest of the plan was already written against — so nothing downstream of §4 had to change its contract.

Two consequences the answer did not spell out, decided here. First, the zero-dependency rule is now a budget (D1); the README, package.json and the CI comments all assert "no runtime dependencies" and each is a documentation change in P1. Second, joi does not ship to the browser (D8) — its browser build is ~53 KB gzipped against a 73.5 KB dashboard, and the previous draft's "share the module through a Vite alias" idea would have put two copies of every rule in play, which is the same class of bug as the stale bundle this workflow started from. The server validates; the form renders the server's verdict. That deletes blueprint.d.ts, the Vite alias and the server.fs.allow: ['..'] hole.

Q2 · Emailing the password → an invitation link

Answer: send an email with a URL carrying a token, where the user sets up their credentials the first time. This is D7, and it is the answer that changed the most sections: R4/R5 in §2, the nullable password_hash and the token kind in §5, a new POST /api/auth/setup and an email-only create body in §7, a rewritten template in §9, an email-only create form in §10.

It also deletes work: the must_change_pw column, the first-login modal, the password field and its Generate button, and the danger callout that existed only to flag a risk we no longer take. The one thing it adds is a dependency on mail actually working — carried by the returned invite.url, the Resend action, and the boot guard.

Q3 · SMTP target → my call, made

Answer: decide it. Two decisions, both in §9.

  1. Use nodemailer instead of hand-rolling SMTP. The previous draft's ~200 lines of EHLO/STARTTLS/ AUTH/quoted-printable was defensible only while mail was a nice-to-have. Q2 put mail on the account-provisioning critical path and Q5 put the server in front of real users; together they make hand-written protocol code the wrong risk to take. Nodemailer has no runtime dependencies of its own, so the cost is one package.
  2. Keep TARGET_SMTP_URL as the only mail knob, and require a real relay when the bind is public. Every transactional provider speaks SMTP, so no provider is baked into the code and switching is one environment variable. The file transport stays the default for local work and CI — but silently writing invitations to a directory on a deployed server would mean nobody can ever log in, so that combination is refused at boot unless explicitly allowed. The one recommendation attached to the decision: send from your own domain with SPF and DKIM, because an invitation in a spam folder is an account that never gets used.

Q4 · Roles → none yet

Answer: every user is an admin; no roles. P5 gains no role checks; the role column is written as 'admin' and never read, kept only so a viewer role is later a query change rather than a migration. §14 now states the consequence plainly: with no roles, an invitation is a full grant, and any user can delete any other — the last-user guard is the only floor under that. Accepted for a single-operator tool; worth revisiting the moment a second kind of user exists.

Q5 · Existing deployments → we will deploy

Answer: the server is going to be deployed. That retires the question as asked — there is no fleet of running instances to bridge onto a login wall, so TARGET_AUTH_DISABLED stops being a migration story and shrinks to what it should always have been: a local-dev and test switch, refused outright on a public bind.

The larger effect is that every default in this plan was chosen for 127.0.0.1 and now has to answer for a public address. The cookie's Secure flag, the origin used to build emailed links, the rate limiter's idea of a client IP, the published seed password and the non-delivering mail transport are each a quiet no-op locally and a real hole once deployed. Rather than scatter that through the plan, it is collected as §17, and the pattern is uniform: the server refuses to start rather than warning, because a warning in a container log is a warning nobody reads.
